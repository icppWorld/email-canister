How email-canister works

email-canister is a product: a repository whose versioned releases hold the code a domain needs to run its own mail on the Internet Computer. A deployment serves one domain with two canisters you control, a C++ backend that receives, stores, indexes and sends mail, and a webmail that users sign in to with Internet Identity, plus a small domain canister for a domain registered elsewhere. The domain also needs a Caffeine app, which is not part of a release: it serves the domain's website, and sends mail through the release's bridge code added to its backend. This page explains each part, where it lives, how mail moves through them, and what you take on by relying on it.

Overview

The whole system

A deployment serves one domain. The diagram groups its parts by where they live: the canisters an email-canister release installs, your domain's Caffeine app, and the services other people run. Mail comes in at the top left through the DFINITY SMTP gateway, and goes out at the top right through Caffeine's mail gateway.

Why a new program rather than a port of an existing mail server: Postfix, Dovecot and their peers depend on processes, threads, sockets and blocking I/O. A canister has none of these. It handles one message at a time, has no sockets, and every call has an instruction limit. email-canister is a small message-driven C++20 program that links two portable libraries: libetpan for MIME parsing and SQLite with FTS5 for storage and search.

Inbound

Receiving mail

The gateway calls smtp_request once per message. That call must answer quickly and must never trap: a trap looks like a temporary failure, and the sending server retries for days. So the call only checks the recipients, removes duplicates and queues the raw message once, for all its recipients. Moving it into each mailbox, parsing and indexing happen later, in separate calls that are allowed to fail.

  • The gateway finds the backend by reading /.well-known/ic-smtp-canister-id from the bare domain. For a domain bought through Caffeine, your Caffeine app serves it. For a domain registered elsewhere, Caffeine serves only www and rewrites its site's list of domains at every deploy, so a domain canister of your own serves the bare domain instead. The brand script writes the same file into the webmail too.
  • Only the SMTP gateway or a controller may call the SMTP methods; anyone else gets 530.
  • The duplicate key is the mailbox, the sender and the Message-ID, or a hash of the content when there is none. The gateway may deliver the same message twice; the inbox shows it once.
  • A mailbox with 100 messages waiting in the queue answers 451, and the sending server retries later. So does every mailbox while 1,000 deliveries wait in all that the canister can work on now, a message counting once per recipient; mail waiting for a mailbox that is being downloaded or held for repair counts only toward that mailbox's 100.
  • The gateway delivers headers and body separately, so the Content-Type header with the MIME boundary is stored with the body.
  • The gateway refuses mail that fails SPF, or whose DKIM signatures all fail. It does not check that the signing domain matches From (DMARC), and passes no result to the canister. The webmail shows the delivering domain, as "via example.com", when it differs from the From domain, and "via an unnamed domain" when the envelope sender is empty.
Storage

One SQLite database per mailbox

Each mailbox has its own SQLite database, a file in a small file system on the canister's stable memory. Beside them, control.db holds the settings, the registry of mailboxes with their members, the queue of incoming mail and the work still to do. Stable memory survives upgrades, so the mail does too. A search, a check, a download and a purge each touch only one mailbox's file, so their cost grows with that mailbox, not with the whole canister. Bodies are rows in the database rather than one file per message: one file per message was measured at about 36 KB of overhead each, which turned an 85 MB database into 1.44 GB of memory.

  • Each call either commits all of its changes or none of them: a trap rolls back the canister's memory, every database included. A call that writes a mailbox file commits it, then control.db, and traps if the second commit fails, which rolls back both.
  • No transaction is held across an await, because other calls may run while one waits.
  • Index maintenance runs in budgeted steps of at most 2000 pages, per mailbox.
  • An admin can check a mailbox with admin_check: SQLite's quick_check of its file, and the file's counters against the registry. One call checks a file up to about 2.6 GB. A file that fails is held for repair: nothing uses it, its new mail waits in the queue, and its members can still download it.
  • Any member can download the mailbox's file from the webmail. While the download runs, new mail waits in the queue and every member's changes are refused, so the copy is consistent. The file opens with any SQLite 3; querying its search index needs SQLite 3.43 or newer.
  • A purge truncates the file by up to 1 GiB per call, then deletes it; its first call removes the members. The registry keeps the mailbox's counters, so a mailbox created again at the address never meets an old UID or bridge key.
  • Each mailbox file has a schema version. After an upgrade that changes it, the ingest timer upgrades each file before it puts new mail in.
  • Every mailbox has a uidvalidity and every message a stable, increasing UID and a change counter, ready for syncing and a later IMAP bridge.
  • Mail is stored as plain text. See Risks.
Outbound

Sending mail

The backend cannot send mail itself: the key to Caffeine's mail gateway is held by a Caffeine app. When Caffeine deploys the app, it sets two environment variables on the app's backend canister, INTEGRATIONS_GATEWAY_URL and INTEGRATIONS_GATEWAY_API_KEY; each send is an HTTPS outcall to that URL with the key, which bills the send to the Caffeine project. So each domain copies the release's bridge/ files into the backend canister of a Caffeine app on the same domain. They add one method, relaySend, which accepts calls only from your backend. That method is the relay bridge: code inside the app's backend canister, not a canister of its own.

The hard part is a call whose answer is lost. The backend cannot tell whether the bridge sent the message. Sending it again could deliver it twice. The outbox solves this with a key per attempt: the bridge remembers the result for each key, and passes the key on to the gateway as its idempotency key. A key names when the canister was installed, the mailbox, the message and the attempt, so no other message ever gets it, even after a reinstall.

  • The sender address is always the address of the mailbox the member sends from, never one from the request. Each sent message records which member sent it.
  • For 7 days from the first send, a retry never goes out twice from two mailboxes: a send's id is kept per sender, and a retry from another of their mailboxes is refused.
  • SENT means the mail gateway accepted the message. Bounces never reach the canister, so the webmail says "accepted for delivery", never "delivered".
  • Measured on mainnet: outbound mail passed DKIM, SPF and DMARC at a large mail provider, a repeated key returned the stored result and only one copy arrived, and a 1,400,000-byte attachment arrived intact.
  • The gateway sends HTML only, adds an open-tracking pixel, and replaces the Message-ID, so replies may not thread in the recipient's mail program.
Access model

Who can see what

Every call to the backend carries the caller's principal. Internet Identity gives each user a principal that is specific to the webmail's sign-in origin. The backend checks that principal on every method; the webmail hiding a button is never the protection.

  • A mailbox can have up to 100 members, all equal, and a person can be a member of several mailboxes. They share its read state, and the reader shows who opened each message.
  • Access is granted only by naming it. Creating a mailbox never adds anyone to an existing one, and Add member names the mailbox and asks for confirmation. A controller can add anyone, their own principal included, so choose controllers as carefully as whoever runs your mail server.
  • Onboarding: the user signs in and sees a "not activated" screen with their principal; an admin creates a mailbox with them as its first member, or adds them to an existing one; the next load shows their mailboxes.
  • The relay bridge accepts relaySend only from your backend's principal, set as one constant in the bridge code. Until it is set, every call is refused.
  • Mail HTML is shown in a sandbox="" iframe with its own strict content security policy, and remote content is blocked, because a script in a message could otherwise take over the session.

What this model does not cover: a controller can install new code that reads everything, and the operators of the nodes running the canister can read its memory. Choose your controllers as carefully as you would choose who runs your mail server.

Components

The components

Backend canister

build/email-canister.wasm
Runs in
Its own canister, one per domain.
Code
C++20 compiled to wasm, from the repository's src/. It links libetpan for MIME parsing and SQLite with FTS5. The release ships the compiled wasm.
Does
Receives mail from the SMTP gateway, stores and indexes it in one SQLite file per mailbox, serves the mailbox API and each member's download of a mailbox to the webmail, sends through the relay bridge, and enforces every access rule.
Interfaces
Candid, described in email-canister.did: SMTP methods, mail_* methods for the mailboxes a user is a member of, admin_* methods for controllers, and timers that call ingest_* methods and outbox_pump on itself.
Limits
One domain per canister. 40B instructions per update call and 5B per query bound every operation; see Measured limits. Stop the canister before upgrading; timers are re-armed afterwards from control.db. An upgrade keeps the mail: the ingest timer takes each mailbox file to the release's schema, one at a time. A canister that runs v0.1.x cannot be upgraded to v0.2.0 or later: it is reinstalled, which erases its mail.

Webmail

webmail/dist
Runs in
An asset canister serves the files, and the app runs in the user's browser.
Code
TypeScript, built with Vite into static files in the repository's webmail/. The release ships the built dist, the same bytes for every deployment.
Does
The mail client users see: a list of their mailboxes; the Inbox, Spam and Trash, with Delete and Undo, actions on several messages at once, stars and blocked senders; reading and search; a compose window with attachments that can be minimised or made full screen; outbox status; a download of a mailbox; and an Admin screen where controllers create mailboxes and manage members and names. It signs in with Internet Identity and calls the backend directly from the browser.
Interfaces
A static app in an asset canister. Its settings (backend id, network, sign-in origin, brand) sit in one JSON block in index.html, so every deployment serves the same JavaScript.
Limits
Sign-ins last up to 7 days. The sign-in origin cannot change once users exist: each user would get a new principal and lose their mailbox. The webmail can also answer on up to 10 custom domains, such as mail.example.com, with the same principals: the brand script lists them in the origin's /.well-known/ii-alternative-origins, which Internet Identity reads.

Brand script

webmail/brand.mjs
Runs in
Your machine, when you prepare a deploy. It never runs on chain.
Code
One JavaScript module for Node.js, shipped in the release next to the webmail.
Does
Turns the generic webmail into one deployment's site: writes the settings block, the title, icons, brand.css with fonts and colours, and .well-known/ic-smtp-canister-id.
Interfaces
node brand.mjs --dist … --out … --backend … --origin … [--network ic|local] [--brand folder]. Plain Node.js 20 or later, no dependencies.
Limits
Refuses unknown roles, missing tokens, unsafe paths and values, and files that do not match the brand manifest's sha256. Warns about low colour contrast. Without a brand, the webmail is greyscale and called "Mail".

Domain canister

domain/domain.mjs
Runs in
An asset canister of your own, on the bare domain. Only a domain registered elsewhere needs it.
Code
Static files that domain.mjs, a JavaScript module for Node.js in the release, writes on your machine.
Does
Serves /.well-known/ic-smtp-canister-id for the SMTP gateway and /.well-known/ic-domains for the IC's custom-domain service, and sends browsers on every other path to https://www.<domain>, keeping the path, query and fragment; without JavaScript, to the website's home page.
Interfaces
node domain.mjs --out … --backend … --domain … [--redirect https://…]. The bare domain's DNS points at the IC and its _canister-id record names this canister.
Limits
Exists because Caffeine connects a domain registered elsewhere only as www, whose CNAME a bare domain cannot hold, and rewrites its site's /.well-known/ic-domains at every deploy. Its controllers can redirect your visitors and your mail, so they belong in your trust model too.

Relay bridge

bridge/
Runs in
The backend canister of your domain's Caffeine app. It is not a canister of its own.
Code
Three Motoko files, lib/relay.mo, mixins/relay-api.mo and types/relay.mo, copied unchanged except for one constant, relayCaller, set to your backend's id. bridge/README.md lists the rest: a mail dependency in mops.toml, and a results map and an include in the actor. Caffeine compiles them with the rest of the app.
Does
Adds one method, relaySend, which hands each message to Caffeine's mail gateway and remembers the outcome per key.
Interfaces
Called only by your backend. Answers #sent, #rejected, #unknown, or #sending while a call is in progress.
Limits
HTML only. No In-Reply-To, References, Reply-To, custom headers, text part or delivery status. Keeps each result for 7 days. A request near 2 MB costs about 16 billion cycles, which a Caffeine engine pays.

Your domain's Caffeine app

not part of the release
Runs in
Its own canisters, a frontend and a Motoko backend, built and deployed by Caffeine. They are not part of an email-canister release.
Code
Your app's own code, plus the bridge code from the release.
Does
Serves the domain's website. For a domain bought through Caffeine it serves the bare domain, including /.well-known/ic-smtp-canister-id, which tells the SMTP gateway where your backend is; for one registered elsewhere it serves only www, and the domain canister serves the bare domain. Holds the mail gateway's key and runs the relay bridge.
Limits
Email sending must be enabled for the domain in the Caffeine project. Outside a Caffeine engine, its backend pays about 16 billion cycles to post a message near 2 MB. Whoever can change these canisters can change the bridge and the /.well-known file, so they belong in your trust model alongside the backend's controllers.

Release

email-canister_vX.Y.Z.zip
Runs in
Nothing: it is a zip on the releases page of the email-canister repository.
Does
Packages everything a deployment needs: the wasm with its sha256 and Candid file, the generic webmail and brand script, the domain script, the bridge, the deploy scripts and the docs, with build provenance.
Interfaces
Published on GitHub by a manual workflow that runs only on main, with release notes, after CI has passed on that commit.
Limits
The wasm is built in a Docker image pinned by digest, so anyone can rebuild a release's commit and compare the hash. The webmail's hash is recorded in the provenance.

Deployment repository

one per domain
Runs in
Your machine, where you run its commands. It is a repository of your own, separate from email-canister.
Does
Holds one domain's choices: which release, the canister ids, the sign-in origin and the brand. It builds nothing.
Interfaces
icp.yaml installs the release wasm pinned to its sha256; the brand script writes build/webmail; configure.sh sets the domain and bridge; check.sh verifies the live deployment.
Limits
Upgrading means vendoring a new release and updating the pins, then redeploying what the release's upgrade notes say changed. A backend upgrade stops the backend, takes a snapshot, upgrades and starts it.

Measurements

Measured limits

Instruction counts on a local replica. The limits are 40B instructions per update call and 5B per query. The first table was measured on a 1.09 GB database of 100,000 messages. With one database per mailbox, the costs that grew with it now grow with one mailbox only.

  • Messages over about 2 MB, or about 1.4 MB of attachments, are refused by the SMTP gateway.
  • An empty mailbox file takes 72 KiB. With the file system's own overhead, the design's prototype measured 112 KiB of stable memory per mailbox.
  • Parsing: 5,000 generated messages, 10% malformed, parsed in wasm with results matching native; 100,000 native mutations under AddressSanitizer and UndefinedBehaviorSanitizer found no error. Nesting of 5,000 levels is rejected cleanly.
  • Charsets decoded: UTF-8, US-ASCII, ISO-8859-1 to -16, Windows-1250 to -1258, KOI8-R and -U, ISO-2022-JP, Shift_JIS, EUC-JP, GB2312, GBK, GB18030, Big5 and EUC-KR. Others fall back to ISO-8859-1.
Before you rely on it

Risks

Running your own mail on canisters moves risks around rather than removing them. These are the ones to accept knowingly, with what reduces each.

RiskWhat happensWhat reduces it
High
Running out of cycles		The canister freezes, stops receiving, and after its freezing threshold is deleted with all mail.A long freezing threshold, a cycles alert or automatic top-up, and users who download their mailbox from the webmail regularly. Check the balance as routinely as a domain renewal.
High
The SMTP gateway is a proof of concept		DFINITY offers no service level agreement. If the gateway is down, senders retry for a few days, then bounce.Download a copy of your mailbox from the webmail regularly. Watch the gateway's announcements, and know how you would move MX records to another provider.
High
Others can read the mail		Node operators can read canister memory, and the mail gateway's operator can read outbound mail. Mail is stored unencrypted.Treat it like a hosted mail service, not end-to-end encryption. Use encrypted attachments for sensitive content. Encryption at rest is on the roadmap.
High
Controllers can change the code		A controller can install a wasm that reads every mailbox, regardless of the access model, or add their own principal as a member of any mailbox.Keep the controller list short and known. Compare the running module hash with a release using check.sh.
Medium
The sign-in origin is permanent		Changing it gives every user a new principal, so nobody can reach their mailbox.Fix the origin before the first user. Each user sets up Internet Identity recovery: losing the identity means losing access.
Medium
Limited spam filtering		Only the gateway's SPF and DKIM checks and allow and block rules apply, and each mailbox's blocked senders, whose mail goes to Spam. There is no content filtering.Keep addresses off public pages where possible. Block a sender from the reader.
Medium
The sender is not verified		Without a DMARC check, a message can show any From address. The webmail names the delivering domain when it differs, but cannot tell a forgery from a mail service's own bounce domain.Confirm unexpected requests, such as payments or password changes, another way.
Medium
MX records out of step with the gateway		If the gateway's hosts change and your MX records do not, mail stops arriving.check.sh compares your MX records with the gateway's.
Medium
Domain expiry		An expired domain stops all mail, and a new owner could receive it.Auto-renew, with a payment method that will still work.
Low
No delivery status		Bounces do not reach the canister. A message can be accepted and still not arrive.The webmail says "accepted for delivery", never "delivered". Confirm important mail with the recipient.
Low
Message size		Messages over about 2 MB are refused, inbound and outbound.Share large files by link.
Low
Reply threading		The mail gateway replaces the Message-ID and supports no In-Reply-To, so replies may not thread for the recipient.Keep subjects intact when replying. Tracked on the roadmap.
Low
A lost send outcome		A send can end as UNKNOWN when its outcome is lost.It is never resent automatically, so it cannot arrive twice. The user checks and resends.
