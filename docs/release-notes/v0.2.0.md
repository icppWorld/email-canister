# v0.2.0

## Overview

A storage and sharing release. Each mailbox gets its own SQLite database, a mailbox can be shared by several people, and one person can have several mailboxes. `control.db` holds the settings, the mailbox registry and the queue of incoming mail, and each mailbox's mail, search index and outbox live in its own file. A search, a check, a download and a purge now cost only that mailbox's own mail. With that come a download of the mailbox for its members, an integrity check for admins, schema versions for mailbox files, and a purge that deletes the file. The relay bridge removes the results it keeps after 7 days and keeps its attempt records across an upgrade of the app. **v0.2.0 does not upgrade a v0.1.x canister: the backend is reinstalled, and its mail is lost.**

## Highlights

- **Shared mailboxes, and several mailboxes per person.** A mailbox has members: up to 100 principals, all equal, download included. One sign-in shows every enabled mailbox a person is a member of. Only admins manage members. A new mailbox's first member, if any, is named in the call that creates it; any other access is its own named action, which the Admin panel confirms, and creating a mailbox never adds anyone to an existing one.
- **Shared read state.** The members share a mailbox's unread state. The reader's "Seen by" lists who opened a message and when, and Sent shows who sent each message.
- **A mailbox list in the webmail.** Each of the person's mailboxes with its unread count; the selected one opens its own Inbox and Sent, usage and download. The mailbox and folder are in the address (`#sales`, `#sales/sent`). Compose sends from the mailbox its From names, and a reply starts from the mailbox the message was read in.
- **An Admin panel for mailboxes, members and names.** "New mailbox" takes an address, an optional first member and an optional quota. Each mailbox lists its members by name, with Add member and Remove, and "People" holds the names that members see.
- **A retry is not sent twice from two mailboxes.** A send's `client_id` is kept per sender for 7 days from the first send. In that time a retry from another of the sender's mailboxes is refused, even after the message was deleted, because it may have gone out already.
- **One SQLite database per mailbox**, at `m/<id / 100>/<id>/mail.db`, as `docs/storage-per-mailbox.md` recommends. `docs/design.md` describes what was built.
- **Delivery in one commit.** `smtp_request` writes only to `control.db`: it queues a message once for all its recipients, reserves their quota and records its dedupe keys, in one transaction. The ingest timer then moves it into each recipient's file, parses and indexes it there, and merges each mailbox's search index in steps.
- **Backlog caps per mailbox.** A mailbox with 100 messages in the queue answers 451, so one stuck mailbox no longer refuses mail for the others: the gateway's check of each recipient defers only those whose mailbox is full. A mailbox that fills up between that check and the delivery still defers the whole message. The canister-wide cap of 1,000 waiting deliveries stays, a message counting once per recipient, and now counts only mail the timer can work on now: mail for a mailbox that is being downloaded, held for repair, or whose file cannot be opened counts only toward that mailbox's cap.
- **Download a mailbox.** "Download a copy" in the webmail saves the mailbox's SQLite file. While it runs, new mail waits in the queue and every member's changes are refused with a message, so the copy is consistent. Only the member who started it can read it, renew it or end it. The webmail renews the download every 2 minutes and reads a failed chunk again; a download that is not renewed ends after 5, and none lasts more than 2 hours.
- **An integrity check for admins.** The Admin panel's "Check" button calls `admin_check`, which runs SQLite's `quick_check` on the mailbox's file and compares its counters with the registry. A file that fails is held for repair: nothing uses it, its new mail waits, and its members can still download it. A later check that finds it sound, or a purge, releases it. One call checks a file up to about 2.6 GB.
- **Schema versions for mailbox files.** The ingest timer upgrades each file to the release's schema before it moves or parses mail into it; meanwhile the webmail retries. v0.2.0 has no upgrade steps yet: the mechanism is for later releases.
- **Purge by truncation.** `admin_purge` shrinks the file by up to 1 GiB per call, then deletes it with its directory. `remaining` now counts bytes. A purge's first call removes the members. A mailbox created again at the address continues the old uids and outbox ids, so no old key can reach it.
- **Quarantine you can act on.** A message whose move into its mailbox failed three times stays in the queue (a call the canister could not run, low on cycles or stopping, does not count), and the Admin panel's "Retry stuck mail" button queues it again (`admin_retry_moves`). `admin_ingest_stats` counts failed moves apart from failed parses. A message that could not be parsed opens as plain text, without attachment links, under a warning, and "Show it formatted anyway" renders it the normal way.
- **Outbox keys that never repeat**, across a reinstall too: `<install time>-<mailbox>-<id>-<generation>`, where the generation rises each time a member sends the message again. Automatic retries keep the key. A message still sending after a day becomes `UNKNOWN` without asking the bridge, well inside the 7 days the bridge keeps its result.
- **Relay bridge:**
  - Removes a kept result 7 days after it was kept, 50 entries per call, so the app's memory stops growing with every message sent.
  - Keeps its record of a post in flight in the results map, so an upgrade of the app while a message is being sent loses nothing. v0.1.4's rule to upgrade the app only while no send is in flight is gone.
  - Accepts an `outboxId` of letters, digits and `-` only, at most 128 characters.
  - Escapes JSON with less work per message, and computes the outcall fee for each attempt from the current balance.
- **Tests and checks.** Native tests of the backend on a mock IC, static checks for C++, Python and the webmail in CI, a test of the real Internet Identity sign-in on the local network, and cost bounds that fail the tests when storage costs grow.
- A `Date:` before 1970 is stored as unknown, and the webmail shows the received time.
- On a local network, the webmail signs in through the network's own Internet Identity.

## Candid API changes

Backend, `email-canister.did`:

- **A mailbox is named in every call.** Every `mail_*` method except `mail_me` takes the mailbox's local part first, for example `mail_list : (text, ListRequest) -> (Page) query` and `mail_send : (text, SendRequest) -> (nat64)`. The caller must be a member of that mailbox. A non-member and an unknown address both get "no such mailbox for this principal".
- **`mail_me`** returns `Me = record { principal; name : opt text; is_controller : bool; mailboxes : vec MailboxInfo }`, in place of one address with its counts and usage. `MailboxInfo` gives each mailbox's local part, address, number of members, message and unread counts, usage, quota and `uidvalidity`.
- **`mail_set_flags : (text, nat64, nat64, nat64) -> ()`** takes the uid, the flags to set and the flags to clear, so two members changing different flags at once keep both. Setting Seen records who opened the message.
- **`FullMessage`** gains `seen_by : vec SeenBy`, each with the principal, its name and when it first opened the message.
- **`OutboxSummary`**, and with it `OutboxMessage`, gains `sent_by : principal` and `sent_by_name : opt text`.
- **`mail_send`** refuses a `client_id` the caller already used from another of their mailboxes in the last 7 days.
- **New, for a mailbox's members:**
  - `mail_export_freeze : (text, opt nat64) -> (ExportInfo)` starts a download, or renews the one whose `started_ns` it names.
  - `mail_export_chunk : (text, ExportChunkRequest) -> (ExportChunk) query` reads up to 1,900,000 bytes of the file.
  - `mail_export_thaw : (text, nat64) -> ()` ends the download it names.
  - Only the member who started a download can renew it, read it or end it.
- **New, for controllers:**
  - `admin_create_mailbox : (NewMailbox) -> ()` replaces `admin_add_entry : (NewEntry) -> ()`. `NewMailbox = record { local : text; quota_bytes : opt nat64; first_member : opt principal }`. It refuses an address in use, and adds the first member in the same call, so a refused one leaves no mailbox.
  - `admin_add_member : (text, principal, opt nat64) -> ()`. The third argument is the mailbox's `uidvalidity` as listed: the call is refused if the address was created again since. `null` skips that check.
  - `admin_remove_member : (text, principal) -> ()`, which also ends that member's download.
  - `admin_set_name : (principal, text) -> ()`. The name is what members see; `""` removes it.
  - `admin_check : (text, opt text) -> (record { result : text; instructions : nat64 })`.
  - `admin_retry_moves : (text) -> (nat64)`.
- **Changed:**
  - `admin_purge`'s `remaining` counts bytes instead of messages.
  - `Entry` loses `principal`, and gains `members : vec Member` (each principal with its name), `vacant : bool`, `uidvalidity : nat64` and `needs_repair : opt text`.
  - `admin_create_mailbox` and `admin_set_quota` trap on a quota above 2^63 − 1 bytes.
  - `StorageTotals.database_bytes` counts `control.db` and the mailbox files, and the new `stable_memory_bytes` is all of stable memory, most of it reserved by the file system: about 64 MiB on a new canister, growing in large steps and never shrinking. The Admin panel shows it as "Stable memory reserved".
  - `IngestStats` gains `quarantined_moves`.
  - Outbox ids and the search cursor are per mailbox. Their types are unchanged.
- **Self-only** (the canister calls them on itself; anyone else is refused): `ingest_process : (nat64, nat64) -> ()` and `ingest_merge : (nat64) -> ()` take the mailbox; `ingest_move : (nat64) -> ()` and `ingest_upgrade_file : (nat64) -> ()` are new.
- The `mail_*` methods that read or change mail answer `busy:` while the mailbox's file is being upgraded and `this mailbox needs repair` while it is held; those that change mail also answer `downloading:` during a download. The webmail retries a `busy:` answer. `mail_me` and the three download methods answer as before, so a held mailbox can still be downloaded.

Relay bridge: `relaySend` is unchanged, apart from the `outboxId` characters above.

## Upgrade notes

**The backend is reinstalled, not upgraded.** v0.2.0 stores mail in a new layout and has no migration from v0.1.x's single `mail.db`. Its `post_upgrade` refuses a canister that holds one, so an upgrade by mistake fails and leaves v0.1.x running with its mail. A reinstall erases every mailbox and all mail.

1. Before the reinstall, save what you need: users forward or save the mail they want to keep, and an admin lists the entries with `admin_list_entries`: each address with its principal, its quota and whether it is disabled. The canister id, its controllers and the webmail's sign-in origin stay, so every user keeps their principal.
2. Stop the backend and take a snapshot (`icp canister snapshot create email-canister --environment ic`). Restoring it brings back v0.1.x with all its mail, should v0.2.0 need to be rolled back. A restore also discards everything v0.2.0 received meanwhile, so before one, users download their v0.2.0 mailboxes from the webmail.
3. Pin v0.2.0 in the deployment repository, whose `icp.yaml` installs the release's wasm only when its sha256 matches. Reinstall the backend (`icp canister install email-canister --mode reinstall --environment ic`), and start it. The wasm sha256 is `1a938b60ed80f019c97599e64c28c925d9fa53930d6c4f2cece55d02da093fdc`.
4. At once, set the domain and the bridge again (`admin_set_domain`, `admin_set_bridge`). Then create each mailbox again with `admin_create_mailbox`, with its v0.1.x principal as `first_member` and its quota where it was not the default. A mailbox is created enabled, so create each one that was disabled without `first_member`, disable it with `admin_set_disabled`, and only then add its principal with `admin_add_member`. Do this from the command line: the Admin panel that can create mailboxes comes with the webmail in step 5. Shared mailboxes and names can wait until then, or be made here with `admin_add_member` and `admin_set_name`. Until an address is created again, mail to it is refused with 550 and bounces for good, so script these calls and run them right after the start, at a quiet time.
5. Deploy the webmail: it calls the new methods. Its `dist` hash is `d00b986e0f29f85ec8b34595d5ad06dbd3e82cd428e728772e7aac381c1d45a3`. The brand format and `brand.mjs` options are unchanged.
6. Copy the new `lib/relay.mo`, `mixins/relay-api.mo` and `types/relay.mo` into the Caffeine app's backend, keeping its `relayCaller`, and deploy the app. The actor needs no change: the bridge keeps its new records in the existing results map, and `moc --stable-compatible` passes against v0.1.4's bridge. Results the old bridge kept get a keep time at the first call that sweeps them, and are removed 7 days later.

The bridge accepts the keys of both backends, so it can be updated before or after the backend.

## Webmail and settings changes

- A list of the person's mailboxes, with an unread count on each; at phone width it becomes a select above the folder tabs. The mailbox and folder are in the address, and the last mailbox chosen is remembered.
- Compose has a From select listing the person's mailboxes, when they have more than one or the draft's mailbox is no longer theirs.
- In a mailbox with more than one member, the reader has a "Seen by" button, and Sent shows who sent each message.
- The Admin panel's "Users" table becomes "Mailboxes", with each mailbox's members by name, Add member and Remove. "People" lists everyone who is a member somewhere, with an editable name. "New mailbox" takes an optional first member and a quota in GB, and "How people get their mail" explains the steps. At phone width each row becomes a block of labelled fields.
- The "not activated" screen says the person's mail opens once an admin gives them a mailbox or adds them to one.
- A "Download a copy" button saves the selected mailbox as `<address>-<date>.sqlite`.
- The Admin panel shows, for each entry, a "Check" button, a "Needs repair" status with the reason on hover, and a "Retry stuck mail" button for mail that could not be moved. It counts failed moves and failed parses apart.
- A message that could not be parsed opens as plain text under a warning, with a button that shows it formatted.
- Every call to the backend retries by itself, up to 3 times, while the mailbox's file is being upgraded.
- On a local network, sign-in goes through the network's own Internet Identity.
- `brand.mjs` options and the brand format: none.

## Known issues

- A mailbox has at most 100 members.
- Only Add member checks that the Admin panel's list is current. Remove, Quota, Disable, Purge, Check and Retry stuck mail on a row read before the address was purged and created again act on the mailbox the address names now. Reload the Admin panel after a purge elsewhere.
- A purge keeps its mailbox's send records for their 7 days, so that a retry from another mailbox stays refused. When the address is created again within those days, a retry by a returning member of a send whose first answer was lost is answered with the purged message, and is not sent.
- The duplicate-send check covers 7 days from the first send of a message. A retry from another mailbox after that is sent again.
- A downloaded mailbox file opens with any SQLite 3, but its search index, `fts`, uses FTS5's `contentless_delete=1`: querying it needs SQLite 3.43 or newer.
- Delivering to several recipients costs several times as many instructions as in v0.1.x, because a message is written to the queue and then into each mailbox in a call of its own: queuing a 2 KB message for 10 recipients takes 12.1M, and moving a 100 KB message into one mailbox 16.9M. Each call stays far below the 40B limit; the cost shows in cycles. Each mailbox takes about 112 KiB of stable memory, of which its empty file is 72 KiB.
- A whole-file check fits in one call up to a file of about 2.6 GB, and a check of the search index alone up to about 0.8 GB. A larger file cannot be checked yet. A file of small mail is about 1.4 times the bytes the quota counts, so a mailbox of small mail filled to the default 2 GiB quota, a file of about 3 GB, is too large; lower its quota where that matters.
- stable-fs scans a whole directory to look up a name that does not exist, so each mailbox's file sits in a directory of its own, and each bucket holds at most 100 mailboxes. Its maintainers suggest folders for now.
- The sender is not verified; see `v0.1.1.md`. DKIM verification in the canister is planned for v0.3.0.
- Posting again after a 5xx, 408, 409 or 425 relies on the gateway answering a repeated idempotency key from its record within its 10-minute replay window; see `v0.1.4.md`.
- A custom domain's sign-in depends on Internet Identity reading `/.well-known/ii-alternative-origins` from the webmail's canister address; see `v0.1.3.md`.
- A domain canister on plain A and AAAA records depends on `icp1.io`'s addresses of today. Use ALIAS or ANAME records where the registrar offers them.
- Replies may not thread in the recipient's mail program, because the mail gateway sets its own `Message-ID`.
- Messages over about 2 MB are refused by the SMTP gateway.
