# v0.12.1

## Overview

A fix release for the IC's limit on a wasm module's exports. The IC now refuses a module with more than 1100 exports of any kind, on install and on every call to a canister already running it. The v0.12.0 wasm exports about 2,300 items, mostly the C++ runtime's and the WASI polyfill's symbols, so a subnet that enforces the limit stops a backend running it. This release builds the backend with the toolchain at 7.1.0, whose wasm exports only its memory and its entry points. Only the backend changes. The webmail differs from v0.12.0's only in the release it shows, and the relay bridge is unchanged.

## Highlights

For maintainers:

- **The toolchain at 7.1.0** (`requirements.txt`, `docker/.env`). The wasm exports only its memory, `canister_init`, `canister_post_upgrade`, `canister_pre_upgrade`, `canister_global_timer`, and one `canister_query` or `canister_update` per method of `src/email-canister.did` plus the runtime's own. The build refuses a module that breaks the IC's export rules.
- **The WASI polyfill at v0.13.2.** The stable file system under the mailbox files stays at 0.13.1, and its chunk size is unchanged, so existing files are read as before.
- **Tests.** `test/test_wasm_exports.py` (`make test-wasm-exports`) checks each built wasm's exports: at most 1100, only memory and `canister_` functions, the system functions, and exactly the methods of its `.did`. The release upgrade test now also upgrades from v0.12.0, with mail in two folders, a calendar event and its secret address.
- **Unbounded calls marked as trusted.** Each `unbounded_wait` passes `IC_TrustedCallee{}`: the calls to the canister itself and to the bridge.

## Candid API changes

None.

## Upgrade notes

**Upgrade the backend in place; it keeps its mail.** The relay bridge is unchanged. The webmail differs only in the release it shows, so redeploying it is optional. Nothing is migrated: `control.db` stays at version 3 and the mailbox files at version 5.

Upgrade while the backend's subnet still runs a replica without the export limit. An upgrade runs the running wasm's `canister_pre_upgrade` first; on a subnet that enforces the limit, a v0.12.0 backend cannot run it, so the upgrade fails until the subnet's replica changes, or until it is done with `pre_upgrade` skipped, which the `icp` command-line tool does not offer.

1. Stop the backend and take a snapshot (`icp canister snapshot create email-canister --environment ic`).
2. Pin v0.12.1 in the deployment repository, whose `icp.yaml` installs the release's wasm only when its sha256 matches. Upgrade the backend (`icp canister install email-canister --mode upgrade --environment ic`), and start it. The wasm sha256 is `WASM_SHA256`.
3. Optionally deploy the webmail, rebuilt with the deployment's brand, so it shows v0.12.1. The release's unbranded `dist` hash is `WEBMAIL_HASH`; the branded output differs from it.
4. Run the deployment's checks. `admin_check` on each mailbox should answer `ok`.
5. Once the upgrade is confirmed, and at the latest 7 days after it, delete the snapshot (`icp canister snapshot delete email-canister <id> --environment ic`).

This holds for a backend running v0.5.0 or later; the release upgrade test starts from v0.5.0 and from v0.12.0. A backend on v0.5.0 to v0.11.0 follows v0.12.0's upgrade notes as well, since this release includes its schema steps, and then deploys this release's webmail.

**Rolling back** to v0.12.0 is possible by installing its wasm in upgrade mode, since nothing was migrated, but v0.12.0 does not run on a subnet that enforces the export limit. Restoring the snapshot also works, and undoes everything since the upgrade, as v0.12.0's notes describe.

## Webmail and settings changes

- The webmail shows release v0.12.1; nothing else changes.
- `brand.mjs` options and the brand format are unchanged.

## Known issues

- The known issues of v0.12.0 stand.
- A backend still running v0.12.0 or earlier stops on a subnet that enforces the export limit, and cannot be upgraded there with the `icp` tool, because the old wasm's `canister_pre_upgrade` no longer runs.
