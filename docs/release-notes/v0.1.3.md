# v0.1.3

## Overview

A webmail release. The webmail can answer on custom domains, such as `mail.example.com`, and users keep the same principal on each address. Plain mail sent through a mail service that adds a tracking pixel, as Caffeine's email service does, now shows on the brand's page. The backend and the relay bridge are unchanged.

## Highlights

- `brand.mjs --custom-domain <host>`, repeatable up to 10 times, writes `.well-known/ic-domains` for the IC's custom-domain service and `.well-known/ii-alternative-origins` for Internet Identity. The principals still come from `--origin`, so a user signs in to the same mailbox on the canister's own address and on each custom domain. The setup guide has a new optional step 9, "Give the webmail a custom domain".
- The reader decides between the brand's page and the white page on what its frame can show. An image the frame never loads, such as a remote open-tracking pixel or an inline image the message doesn't carry, no longer keeps plain mail on the white page, unless it could paint something of its own, such as a background. An image the message carries itself still does. The message is shown as before.
- The setup guide says that Caffeine's email service adds an open-tracking pixel to the mail a deployment sends.

## Candid API changes

None.

## Upgrade notes

The backend wasm is the same as in v0.1.0 to v0.1.2, sha256 `16d977d82dcc40490667993468ff8aabb5d3cbb99d61fffa462d0cf84b64ebdf`, so the backend canister needs no upgrade. The relay bridge and the domain canister are unchanged.

Update the deployment's release pins to this release, run `webmail/brand.mjs` on this release's `webmail/dist` with the deployment's settings, and deploy its output to the webmail canister. From v0.1.0, read the upgrade notes of `v0.1.1.md` first: `brand.mjs` became stricter about role values and font families there.

To give the webmail a custom domain, follow the setup guide's step 9. Keep `--origin` as it is: changing it gives every user a new principal.

## Webmail and settings changes

- `brand.mjs` accepts `--custom-domain <host>`, which needs `--origin` to be the webmail's own `https://<webmail id>.icp0.io` (or `.ic0.app`), because Internet Identity reads the list there. It refuses a host that is not a lower-case name within DNS's length limits, an IP address, a canister address under `icp0.io`, `ic0.app` or `icp-api.io`, a host given twice, and more than 10 hosts. Without the option, the output is the same as before. `domain.mjs` applies the same length limits to `--domain`.
- The webmail serves `/.well-known/ii-alternative-origins` as `application/json`, with CORS `*` like the other `.well-known` files.
- Plain mail with an image the frame cannot show takes the brand's page, when the image carries only the attributes and styles of a tracking pixel: sizes, `display`, `visibility`, `opacity`, and a border whose image is `none`. Before, any `<img>` kept the white page. An image counts as shown when its `src`, or a `srcset` candidate, is a `data:` URL.

## Known issues

- When the mail gateway rate-limits a send with HTTP 429, the relay bridge marks the message rejected instead of retrying it; sending it again from the webmail works. Some messages that were never sent are reported as outcome unknown. Both are fixed in v0.1.4. The v0.1.1 and v0.1.2 notes said v0.1.3.
- A custom domain's sign-in depends on Internet Identity reading `/.well-known/ii-alternative-origins` from the webmail's canister address. It was not tested against Internet Identity before this release, because only a registered domain can test it.
- The sender is not verified; see `v0.1.1.md`. DKIM verification in the canister is planned for v0.2.0.
- A domain canister on plain A and AAAA records depends on `icp1.io`'s addresses of today. Use ALIAS or ANAME records where the registrar offers them.
- Replies may not thread in the recipient's mail program, because the mail gateway sets its own `Message-ID`.
- Messages over about 2 MB are refused by the SMTP gateway.
