# v0.12.2

## Overview

A performance release. The backend is built with the toolchain at 7.2.0rc1, whose Candid decoder and encoder are several times faster, most of all for large blobs. Accepting a message near the largest size now costs about half the instructions, and the queries that return large blobs gain more. Only the backend changes. The webmail differs from v0.12.1's only in the release it shows, and the relay bridge is unchanged.

## Highlights

For maintainers:

- **The toolchain at 7.2.0rc1** (`requirements.txt`, `docker/.env`), a release candidate. The wasm still exports only its memory and its entry points.
- **No copy of the SMTP argument or the bridge's reply.** `decode_smtp_request` reads the argument, up to 2 MB, by reference, and the outbox reads the bridge's reply the same way.
- **Measured** on the local replica (`smtp_request`, instructions):

  | Case                     |  v0.12.1 |  v0.12.2 | Gain  |
  |--------------------------|---------:|---------:|------:|
  | 2 KB, to 10 recipients   |    13.2M |    12.4M | 1.07x |
  | 100 KB                   |    24.5M |    17.0M | 1.44x |
  | 1.9 MB                   |   250.6M |   124.6M | 2.0x  |

  The toolchain's own benchmark on this canister's calls puts the encoding of `mail_list`, `mail_get` and `mail_export_chunk` replies at 8 to 36 times faster.
- **Tests:** `test_storage.py` bounds `smtp_request` of a 1.9 MB message at 175M instructions.

## Upgrade notes

**Upgrade the backend in place; it keeps its mail.** The relay bridge is unchanged. The webmail differs only in the release it shows, so redeploying it is optional. Nothing is migrated: `control.db` stays at version 3 and the mailbox files at version 5.

1. Stop the backend and take a snapshot (`icp canister snapshot create email-canister --environment ic`).
2. Pin v0.12.2 in the deployment repository, whose `icp.yaml` installs the release's wasm only when its sha256 matches. Upgrade the backend (`icp canister install email-canister --mode upgrade --environment ic`), and start it. The wasm sha256 is `462e5902a9147abb938e860f8db9c64a0df628a0684588d9311c4eb032f4798e`.
3. Optionally deploy the webmail, rebuilt with the deployment's brand, so it shows v0.12.2. The release's unbranded `dist` hash is `d5329e5319b17153419ef2092541f2ca082fc6017e17a09d76d195928a00e36d`; the branded output differs from it.
4. Run the deployment's checks. `admin_check` on each mailbox should answer `ok`.
5. Once the upgrade is confirmed, and at the latest 7 days after it, delete the snapshot (`icp canister snapshot delete email-canister <id> --environment ic`).

This holds for a backend running v0.5.0 or later; the release upgrade test starts from v0.5.0 and from v0.12.0. A backend on v0.5.0 to v0.11.0 upgrades straight to this release's wasm, which runs v0.12.0's schema steps itself. It takes v0.12.0's Candid additions and order from v0.12.0's upgrade notes: the backend first, then this release's webmail, which is then required. It does not install the v0.12.0 wasm.

**Rolling back** to v0.12.1 is possible by installing its wasm in upgrade mode, since nothing was migrated. Restoring the snapshot also works, and undoes everything since the upgrade, as v0.12.0's notes describe.
