# v0.12.0

## Overview

A release for a calendar in every mailbox. Its members see and change it in the webmail, and can share it at a secret address that any calendar app which subscribes by URL can follow, as a standard iCalendar (`.ics`) file. The backend gains the calendar's API, two schema steps and an HTTP endpoint for the address; the webmail gains a Calendar page. The relay bridge is unchanged.

## Highlights

For members, in the webmail:

- **A Calendar page for each mailbox.** A month grid with the previous and next month and This month, and below it the month's events by day. New event, or a click on a day number, opens the event form; a click on an event opens it. Every member of the mailbox sees and changes the same calendar.
- **The event form.** Title, start and end date and time or all day, location and notes. Times are entered and shown in the browser's time zone, and stored in UTC, so every calendar app shows them in its own zone; an all-day event is stored as dates. Events are one-off: there are no repeats.
- **A secret address.** "Subscribe from a calendar app" makes the calendar's address, after a confirmation that anyone who has it sees every event. The dialog shows it with Copy, makes a new address, which ends the old one, and stops sharing. A calendar app subscribes by URL with the copied https address. The address is `/cal/<token>.ics` on the backend canister, with a 128-bit token from the IC's randomness.
- **Events written another way.** An event with more than the form writes, such as a repeat, a time zone or an alarm, written by a member through the API or by a later release, shows once, at its start, and opens read-only: it can be deleted, not changed, so a save never drops what the form cannot show.
- **Modal dialogs.** While an event or Subscribe dialog is open, nothing else in the webmail can be used, and while its save, delete or address change runs its Close and Escape wait. So the outcome, a failure included, shows in its dialog.

For maintainers:

- **Backend.** `src/store/calendar_store.{h,cpp}` stores each event as the `VEVENT` block the webmail wrote, checks its shape and never reads its dates; `src/api/calendar_api.cpp` holds the Candid methods and the feed. The feed is answered by `http_request_update`, after the query `http_request` has found the address and asks for the upgrade, so the reply is certified.
- **The address ends** when a member is removed (who may have copied it), when the mailbox is disabled (and it is not back when the mailbox is enabled again), and when the mailbox is purged. The token is kept in `control.db` only, so a downloaded mailbox file carries no live address.
- **Webmail.** `webmail/src/ical.ts` builds and reads events with `ical.js`; the calendar's dialogs are native modal `<dialog>` elements. `IconButton` is a plain button by default and submits a form only with `type="submit"`.
- **Tests:** `test/canister/test_calendar.py` (the API, the refusals, the feed and when its address ends), the release upgrade test now also checks the calendar of an upgraded mailbox, and `webmail/e2e/calendar.spec.ts`.

## Candid API changes

New types: `CalendarEvent`, `TimeZone`, `EventRequest`, `EventWindow`, `EventPage`, `HeaderField`, `HttpRequest`, `HttpUpdateRequest` and `HttpResponse`.

New methods, each taking the mailbox's local part first and open to its members only:

- `mail_cal_list : (text, EventWindow) -> (EventPage) query`: the events overlapping `[from, to)`, in UTC seconds, paged.
- `mail_cal_put : (text, EventRequest) -> ()`: adds or replaces an event, by uid. At most 5,000 events of up to 16 KiB, and at most 4 zones an event names. The webmail sends no zones: its events are in UTC or all-day.
- `mail_cal_delete : (text, text) -> (bool)`: true when there was one.
- `mail_cal_feed : (text) -> (opt text) query`: the token of the secret address, or null while the calendar is not shared.
- `mail_cal_feed_reset : (text) -> (text)`: a new address; the old one stops.
- `mail_cal_feed_stop : (text) -> ()`: stops sharing.

New HTTP methods, open to anyone: `http_request : (HttpRequest) -> (HttpResponse) query` and `http_request_update : (HttpUpdateRequest) -> (HttpResponse)`, for `GET` and `HEAD` of `/cal/<token>.ics`. An unknown path or address answers 404, another method on a live address 405 (`Allow: GET, HEAD`), and a mailbox whose file is busy, such as being upgraded, 503 with `Retry-After: 60`.

No existing method changes.

## Upgrade notes

**The backend is upgraded in place, and keeps its mail.** Upgrade the backend first, then deploy the webmail: the v0.12.0 webmail needs the `mail_cal_*` methods, while the v0.11.0 webmail works on the v0.12.0 backend. Users reload any webmail tab left open from before the deploy; the webmail's update banner offers it. The relay bridge is unchanged: nothing to copy into the bridge's app.

This holds for a backend running v0.5.0 or later; the release upgrade test starts from v0.5.0. A backend on an earlier release first upgrades as v0.5.0's upgrade notes say.

The Candid interface only grows: no existing method changes.

1. Stop the backend and take a snapshot (`icp canister snapshot create email-canister --environment ic`).
2. Pin v0.12.0 in the deployment repository, whose `icp.yaml` installs the release's wasm only when its sha256 matches. Upgrade the backend (`icp canister install email-canister --mode upgrade --environment ic`), and start it. `post_upgrade` takes `control.db` to version 3. The wasm sha256 is `d865c1ce9a2930ebf0ed9e73adb2c69c5e638affcf2982585a9606cb972a31ab`.
3. Deploy the webmail, rebuilt with the deployment's brand. The release's unbranded `dist` hash is `dfa21b27f7e50e2e8956f0aa25d5f8f7e29f2299edc7bea7d43a77274333136c`; the branded output differs from it. The brand format and `brand.mjs` options are unchanged.
4. Run the deployment's checks. The ingest timer upgrades each mailbox file to version 5, one file per step, taking turns with incoming mail. The step only creates the calendar's empty tables, so each file takes one short step. Until a mailbox's file is upgraded, its members' calls answer `busy:`, and the webmail says the mailbox is being upgraded. `admin_check` on each mailbox afterwards should answer `ok`. A file over about 2.6 GB does not fit in one whole-file check: check it table by table (`admin_check("<local>", opt "<table>")`).
5. Check the address: in the webmail, Calendar, "Subscribe from a calendar app", make a secret address, and fetch it (`curl -s <address> | head -3` shows `BEGIN:VCALENDAR`). Stop sharing again if it was only a check.
6. Once the upgrade is confirmed, and at the latest 7 days after it, delete the snapshot (`icp canister snapshot delete email-canister <id> --environment ic`).

**Rolling back** is possible only by restoring the snapshot: stop the backend, restore the snapshot (`icp canister snapshot restore email-canister <id> --environment ic`), start the backend (`icp canister start email-canister --environment ic`), then pin again in the deployment repository the release it ran before the upgrade, and deploy that release's webmail: it matches the restored backend, which the v0.11.0 webmail does not when the backend ran a release before v0.7.0. A restore puts the whole canister back as it was at the snapshot, so it undoes everything since the upgrade, and only that:

- **Mail.** Mail received since the upgrade is lost. Members download their mailboxes from the webmail first.
- **Calendars.** Every event and every secret address made since the upgrade is lost, and those addresses stop working.
- **Admin changes** made since the upgrade are undone: members, mailboxes disabled or purged, quotas, names, domain and bridge settings. Until they are made again, a member removed since the upgrade can read and send from the mailbox again. So before the restore, an admin prepares a script that makes those changes again, and runs it as soon as the backend is started.
- **Members' changes** made since the upgrade are undone: mail moved, filed in Spam or deleted since, by the cleanup too, comes back to where it was, and the blocks and unblocks made since are undone. Folders, blocks and read states from before the upgrade stay.
- **Sending.** Each mailbox's outbox counter goes back, so for 7 days after a message was sent on v0.12.0 a new send can get its bridge key, and the relay bridge then answers with that message's result without sending. Mail waiting to be sent in the snapshot is posted again. So restore within 7 days of the upgrade, start the canister at once, and for 7 days have members confirm important mail by another way.

Do not install an earlier release over the upgraded canister: it refuses `control.db` version 3 ("control.db is from a newer release"), so its `post_upgrade` traps, the install fails, and v0.12.0 keeps running. An earlier release would also refuse the version-5 mailbox files.

## Webmail and settings changes

- A Calendar page, at `#<mailbox>/calendar`, with its link in the navigation and a calendar icon.
- The webmail bundles one more package, `ical.js` (MPL-2.0, unmodified); `THIRD_PARTY.md` names it.
- `webmail/public/.ic-assets.json5`, the `brand.mjs` options and the brand format are unchanged.

## Known issues

- Calendar apps fetch a secret address on their own schedule, some only every few hours, so a change can take that long to show there. They ignore reminders.
- Anyone who has the secret address reads the whole calendar. Each fetch is an update call that the backend pays for in cycles. A new address, or stopping the sharing, ends the old one at once.
- There is no one-tap subscribe link: a `webcal:` link is fetched over plain http by many apps, which would show the token to the network, and `webcals:` is not taken everywhere. The address is copied and pasted into the calendar app's subscribe by URL.
- The secret address is on the backend canister's own address, `https://<backend id>.icp0.io/cal/<token>.ics`, not on the mail domain.
- The address serves every event that has not ended, or ended in the last year, up to about 1.9 MB; older events stay in the calendar but are left out of it.
- There are no invitations by mail, and no reminders. The relay cannot send a `text/calendar` part.
- One calendar per mailbox, and no subscribing to other calendars yet.
- No repeating events, and no time zone per event: the form makes one-off events in the browser's time zone. An event written another way with a repeat shows only once, at its first time, in the webmail; calendar apps that subscribe show all its times.
- An event written another way in a named time zone shows in the webmail as if in the browser's zone, so its time can be off by the difference; calendar apps show it right.
- A time that the clocks skip when they go forward is refused. A few historical zone changes are not handled: a day a zone skipped entirely, and offsets with seconds before 1972.
- Events before 1970 are refused.
- The browser's Back, while a save, a delete or an address change runs, leaves the calendar: the change still ends, but its outcome, a failure included, does not show, and the calendar opened again may load before it lands. On a phone, repeated back gestures can also close the dialog itself, with the same result.
- An HTML file goes to the recipients as it is, scripts and forms included; their mail programs decide what to show. The preview and Sent show the cleaned copy the reader would show.
- A message goes to at most 50 recipients, To, Cc and Bcc together. A larger list takes several messages; Compose does not split it.
- The browser's own reload, a pull to refresh on a phone, or closing the tab loses a message being written, or the outcome of an event being saved, without asking. Only the webmail's own Reload asks.
- A send from a full mailbox does not free its expired mail: the send is refused, and the refusal marks nothing. Empty Trash or Empty Spam frees room at once, and the next mail that arrives, or a move of mail, starts the cleanup.
- No timer cleans expired mail by itself: a mailbox is cleaned after a delivery, a move or a 452.
- At 1,000 blocked addresses, a new block replaces the oldest without saying so: mail from the oldest address reaches the Inbox again.
- The known issues of v0.11.0 not repeated here still apply, those of the message reader and of sending an HTML file among them; its notes list them.
