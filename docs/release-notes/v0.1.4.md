# v0.1.4

## Overview

A relay bridge and outbox release. The bridge retries a rate-limited or lost send within the mail gateway's replay window instead of storing it as rejected or unknown, reports `#rejected` only for mail that was certainly not sent, and escapes and checks what it posts. The backend gives every outbox message a bridge key that no other message gets, which fixes a deleted message's key being handed to the next one. The release also carries the storage design for v0.2.0: one SQLite database per mailbox.

## Highlights

- **Rate limits and lost outcomes are retried.** An HTTP 429, 408, 409, 425 or 5xx, a response lost after one immediate retry, or an outcall the IC could not make just now leaves the message `#sending`. Each repeated call in the first eight minutes of the gateway's 10-minute replay window posts again with the same idempotency key, so the gateway sends it at most once; the last two minutes cover an outcall that times out and its one retry. Only after that does an outcome that may have been sent become `#unknown`; one that no attempt posted, or that the gateway rate limited each time, becomes `#rejected`.
- **`#rejected` means certainly not sent.** Missing gateway settings, a missing API key, an invalid `outboxId` or attachment, a request over the IC's 2 MB outcall limit once escaped, a redirect, and a 4xx other than 408, 409, 425 and 429 report `#rejected`, unless an earlier attempt of the message may have sent it. After a lost response, a retry that was refused or rate limited counts as possibly sent. Sending the message again from the webmail makes a new attempt with a new key.
- **One post per message in flight.** A repeated call while a post is in flight answers `#sending` and does not post. `relaySend` no longer calls its own canister on the way, which saves a message per send and removes a way for it to fail.
- **Strict JSON.** Every control character in the subject, body, addresses and file names is escaped as `\u00xx` instead of being dropped, and an attachment that is not standard base64 is refused before anything is posted. Error text kept with a result is cut to 1,024 characters.
- **Size counted as posted.** The backend counts a message's size the way the bridge posts it, with quotes, backslashes and control characters escaped in JSON, so a message that would be too large to post is refused when it is sent instead of being rejected later.
- **Bridge keys never repeat.** SQLite gave the id of a deleted newest outbox message to the next message, and with it the same bridge key, so the bridge could answer with the deleted message's result and never send the new one. Outbox ids now come from a counter that only rises, so no id is given out twice, and a reply from the bridge can no longer reach a new message that took a deleted one's id. A key also names when its message was created, because the first message after the upgrade can still get the id of one deleted before it.
- **Bridge tests.** `make test-bridge` runs the bridge in a Caffeine-style app on PocketIC against mocked gateway answers, and CI runs it.
- **Storage design.** `docs/storage-per-mailbox.md` recommends one SQLite database per mailbox plus a control database, with the file layout in the canister, measurements from a prototype, pros and cons, and the design questions answered. The roadmap makes it v0.2.0.
- The design document and the explainer no longer say consistency checks are paged: no consistency check runs yet.

## Upgrade notes

Both the backend and the relay bridge change. The webmail and the domain canister are unchanged: the webmail build is the same as in v0.1.3, `dist` hash `3f97a475b342fca0bb767c59a766e408c0c051af719d803b9437758cc5b7b84d`, so redeploying it is not needed.

**Backend.** The wasm sha256 is `bd979c441c5d1d6b1d5a93b1cb3aa083f7123e59a4ffff7620c78e5731e885e7`. Stop the canister, upgrade it, and start it again, as for any backend upgrade. `post_upgrade` migrates the database from schema version 1 to 2: it adds a column to the outbox table, which marks the messages whose bridge key names their creation time. Outbox messages created before the upgrade keep the key they had, so a message queued or in doubt during the upgrade is never sent twice; messages created after it get keys with their creation time, and ids from a counter the backend keeps in its settings table. Messages a rollback to v0.1.3 creates keep v0.1.3's keys after a new upgrade. A rollback itself gives v0.1.4's messages old-style keys, so roll back only while no message is being sent: one in doubt would be posted under a new key. A rollback also brings back the bug this release fixes, so after one, delete no outbox message until the backend runs v0.1.4 again: a new message could get the deleted one's key and its kept result. The migration is tested across an upgrade with queued mail.

**Relay bridge.** Copy the new `lib/relay.mo`, `mixins/relay-api.mo` and `types/relay.mo` into the Caffeine app's backend, keeping its `relayCaller`, and deploy the app. The actor needs no change: the mixin keeps its in-flight record in a `transient` variable, and the stable signature is the same, so no migration is needed. Results the old bridge kept stay as they are: the backend already took them as final.

Backend and bridge can be upgraded in either order.

## Known issues

- The bridge never evicts kept results. A sent result takes about 150 bytes; a rejected or unknown one adds its error text, at most 1,024 characters. Eviction is planned for v0.2.0.
- Posting again after a 5xx, 408, 409 or 425 relies on the gateway answering a repeated idempotency key from its record, as it does within its 10-minute replay window. A gateway that sent a message but failed before recording the key would send it again.
- A reject from the management canister counts as possibly sent, because it is not certain that every such reject comes before the request leaves. The bridge therefore checks the request's size before posting. It does not check its cycles, because a Caffeine engine reports a balance of 0 and pays for outcalls itself: a message a bridge with too few cycles could not post ends as `#unknown`. Keep the app's cycles well above its freezing threshold.
- Upgrade the Caffeine app while no send is in flight, for instance with the backend's outbox empty. The bridge's record of a post in flight does not survive an upgrade, so a call right after it posts again while the old post may still be under way; the gateway then sees the same key twice at once.
- A message sent while no bridge is set is retried and marked UNKNOWN after 15 minutes, as in v0.1.3, although it never left the canister.
- The backend gives a message 15 minutes from its first attempt; the bridge's window starts when the bridge first receives it. After the bridge was unreachable for several minutes, the backend can mark a message UNKNOWN that the bridge would have reported as rejected.
- A `#sending` result stays kept when the backend stops asking before the bridge's replay window has ended, for instance after the bridge canister was stopped for several minutes. It takes a few bytes and changes nothing else. The bridge's in-memory record of that message's last attempt, with up to 1,024 characters of error text, stays until the app's next upgrade.
- The sender is not verified; see `v0.1.1.md`. DKIM verification in the canister is planned for v0.3.0.
- A custom domain's sign-in depends on Internet Identity reading `/.well-known/ii-alternative-origins` from the webmail's canister address; see `v0.1.3.md`.
- A domain canister on plain A and AAAA records depends on `icp1.io`'s addresses of today. Use ALIAS or ANAME records where the registrar offers them.
- Replies may not thread in the recipient's mail program, because the mail gateway sets its own `Message-ID`.
- Messages over about 2 MB are refused by the SMTP gateway.
