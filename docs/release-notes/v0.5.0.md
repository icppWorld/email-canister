# v0.5.0

## Overview

Spam blocks the sender in one click. Marking mail as Spam, in the reader or on ticked messages in the list, files it in Spam and blocks its `From` address. One Undo brings the mail back and lifts the block. Not spam does the reverse. The backend makes this possible by listing each message's `From` address, from a new mailbox schema step that only adds a column. The relay bridge is unchanged.

## Highlights

- **Spam blocks the sender.**
  - In the reader, and on ticked messages in the list, Spam moves the mail to Spam and blocks the `From` address of each message that moved. The note reads "Message moved to Spam and x@example.com blocked", or "3 messages moved to Spam and 2 senders blocked" for several.
  - Undo brings the messages back and lifts the blocks. A block that was there before stays.
  - Spam never blocks an address of the mailbox's own domain or its subdomains, since spam often claims to come from the recipient. Mail with no `From` address only moves.
  - When a block is refused, or the list of blocked senders cannot be read, the mail still moves and the note says what failed. The blocks for several senders run side by side, and a refused one stops no other.
  - The note's separate Block sender button is gone. In the Spam folder, the reader's ⋮ menu keeps Block sender.
- **Not spam lifts the block.** In the Spam folder, Not spam moves the mail to the Inbox and unblocks its `From` address. Undo moves the mail back and blocks the address again. A block of the envelope sender stays: unblock it on the Blocked senders page.
- **Undo puts back every change it tried.** A block whose reply was lost may have gone through, so Undo lifts it as well. A block or unblock that Undo cannot make still lets the messages come back, and the note says why.
- **A Blocked senders button** at the top of the Spam folder's list, besides the one in the header's ⋮ menu.
- **The message list gives each message's `From` address** (`sender_address`), so the webmail can block the sender of mail it has not opened.
- **Faster CI:** a run takes about 6 minutes instead of 27. A pull request that changes only docs skips the build and tests, and a push to `main` reuses a pull request's passed run for the same tree.
- **Tests:** native, replica and browser tests for each change and for every review fix. The release upgrade test now starts from v0.4.0.

## Candid API changes

- `Summary` gains `sender_address : text`: the `From` address alone, as `mail_block` takes it. It is empty when the message is not parsed yet, or has no address that `mail_block` would take. It keeps the `From` header's letter case, while `mail_block` and `mail_blocked` keep A to Z in lower case: compare them with A to Z lowered.
- So the records these methods return gain the field, with their arguments unchanged:
  - `mail_list : (text, FolderRequest) -> (Page)`, where `Page` holds `Summary` records;
  - `mail_search : (text, SearchRequest) -> (Page)`;
  - `mail_get : (text, nat64) -> (FullMessage)`, where `FullMessage` holds one.

A client built for v0.4.0 keeps working: Candid lets it ignore the new field.

## Upgrade notes

**The backend is upgraded in place, and keeps its mail.** Upgrade the backend first, then deploy the webmail: the v0.5.0 webmail needs `sender_address`, which a v0.4.0 backend does not send, while the v0.4.0 webmail works on the v0.5.0 backend. Users reload any webmail tab left open from before the deploy. The relay bridge is unchanged: nothing to copy into the Caffeine app.

This holds for a backend running v0.3.0 or v0.4.0, whose wasm is the same. One still on v0.2.0 upgrades as v0.3.0's upgrade notes say, with v0.5.0's wasm.

1. Stop the backend and take a snapshot (`icp canister snapshot create email-canister --environment ic`).
2. Pin v0.5.0 in the deployment repository, whose `icp.yaml` installs the release's wasm only when its sha256 matches. Upgrade the backend (`icp canister install email-canister --mode upgrade --environment ic`), and start it. The wasm sha256 is `093dee53a3c369bd4b345f74f2d5d141bc4882b05a1d73183a27d076e7b39882`.
3. Deploy the webmail, rebuilt with the deployment's brand. The release's unbranded `dist` hash is `f12774644d20d11543f04747b9001677bf00bf8a05e1a89f89535b90e636478d`; the branded output differs from it. The brand format and `brand.mjs` options are unchanged.
4. Run the deployment's checks. The ingest timer upgrades each mailbox file to version 3, one file per step, taking turns with incoming mail. The step only adds a column, so each file takes one short step. Until a mailbox's file is upgraded, its members' calls answer `busy:`, and the webmail says the mailbox is being upgraded. `admin_check` on each mailbox afterwards should answer `ok`. A file over about 2.6 GB does not fit in one whole-file check: check it table by table (`admin_check("<local>", opt "<table>")`).
5. Once the upgrade is confirmed, and at the latest 7 days after it, delete the snapshot (`icp canister snapshot delete email-canister <id> --environment ic`).

**Rolling back** means stopping the backend and restoring the snapshot (`icp canister snapshot restore email-canister <id> --environment ic`), then deploying the v0.4.0 webmail again. A restore puts the whole canister back as it was at the snapshot, so it undoes everything since the upgrade, and only that:

- **Mail.** Mail received since the upgrade is lost. Members download their mailboxes from the webmail first.
- **Admin changes** made since the upgrade are undone: members, mailboxes disabled or purged, quotas, names, domain and bridge settings. A restored canister is stopped and answers nobody, so an admin prepares a script that makes those changes again and runs it when the canister is started.
- **Members' changes** made since the upgrade are undone: mail moved, filed in Spam or deleted since comes back to where it was, and the blocks and unblocks made since, by Spam and Not spam among them, are undone. Folders, blocks and read states from before the upgrade stay.
- **Sending.** Each mailbox's outbox counter goes back, so for 7 days after a message was sent on v0.5.0 a new send can get its bridge key, and the relay bridge then answers with that message's result without sending. Mail waiting to be sent in the snapshot is posted again. So restore within 7 days of the upgrade, start the canister at once, and for 7 days have members confirm important mail by another way.

Do not install v0.4.0 or v0.3.0 over upgraded files: they open only version-2 files, so every upgraded mailbox answers that it needs a newer release until v0.5.0 is installed again.

## Webmail and settings changes

- Spam, Not spam, Undo and the Blocked senders button, as above. The Inbox reader's Spam and the list's Spam now also block; nothing asks for confirmation.
- The `brand.mjs` options and the brand format are unchanged.

## Known issues

- Every Spam uses one of the mailbox's 1,000 blocked-address places. Once they are used, each Spam's note says the block failed; unblock addresses on the Blocked senders page to make room.
- Undo of a Spam can lift a block of the same address that another member, or a second Spam click, made at the same moment.
- Spam blocks the `From` address the message claims, which nothing verifies. Spam that forges a real sender's address blocks that sender, whose genuine mail then goes to Spam until the address is unblocked. Only the mailbox's own domain and its subdomains are spared.
- Spam only moves the mail, and its note does not say that no block was made, when the list has no `From` address for it: mail parsed after the list was loaded (until the list's next refresh, within 20 seconds), quarantined mail, and a `From` address `mail_block` refuses.
- Not spam does not lift a block of the envelope sender, which also files mail in Spam; the next such mail goes to Spam again. Unblock the envelope sender on the Blocked senders page.
- A block or unblock by Spam or Not spam whose reply is lost after the canister made it shows as failed in the note. Undo puts it back; without Undo, the Blocked senders page shows the address.
- Undo of a Not spam blocks the address again in the name of the member who clicked Undo, at that time.
- A message that another member deleted meanwhile counts as moved, in the note's count, and its sender is blocked.
- A Block sender from the Spam folder's ⋮ menu whose reply is lost after the canister stored it shows as failed. The Blocked senders page shows the address.
- Mark unread in the list's toolbar or a row's hover action, on the message that is open, can race the reader's own mark as read, so the message can end up read. The reader's ⋮ Mark unread waits for it.
- At phone width, the device's back gesture leaves the webmail rather than returning from a message to the list. The reader's Back button returns.
- In full screen, the keyboard focus is not held inside the compose window.
- An Older mail click in Sent made while the list's first page reloads does nothing; click it again.
- A delete or move made in one browser shows in another member's list on its next refresh, within 20 seconds.
- Mail deleted for good, by Delete forever, Empty Trash or Empty Spam or after 30 days, leaves the listing and the search at once, but its bytes can stay in the mailbox file until SQLite reuses the space. A member who downloads the file can recover it with SQLite tools. A purge removes the whole file.
