# v0.14.2

## Overview

A second webmail fix for a phone that wakes from sleep. A read under way when the phone slept, such as the Inbox's timed refresh, failed at once on waking with *Backoff strategy exhausted after 2 attempts. Request ID: …*, which showed until the next refresh got through. The agent gives up on a request once 15 minutes have passed since it began, which a request under way during a sleep that long has passed when the phone wakes. The webmail now gives the agent the same retries without that time limit. The read is sent again, refused for its expiry, then signed anew and read, so nothing shows. The backend and the relay bridge are unchanged.

## Highlights

For people using the webmail:

- **No error after a phone wakes from a long sleep.** A read under way when the phone slept is sent again when it wakes. The network refuses that copy, as its expiry passed during the sleep, and the read is then signed anew and gets through, as v0.14.1 does for a request signed before a sleep.
- **An action under way during a sleep says to check it.** An action, such as a star, a move or a send, is not signed anew: it may have run already. Sent again on waking and refused for its expiry, it says *The connection to the mail server was interrupted. Check whether this went through before trying again.*

For maintainers:

- `createBackend` in `webmail/src/api.ts` passes the agent `retryDelays` as its `backoffStrategy`, with `retryTimes` of 3. Its delays are the agent's default ones, 750 ms, 1.125 s and about 1.7 s, each ±50%, and it stops after those 3 retries by itself, so a request is sent at most 4 times. The agent's default, `ExponentialBackoff`, also returns no delay once 15 minutes have passed since it was made, at the request's start; that limit is what the sleep ran past. The agent does not export `ExponentialBackoff`, so the webmail has its own.
- A resend is the same signed request. The network runs an update at most once within its expiry, and refuses any request after it, so the retries add no way for an action to run twice.
- Tests: a new Playwright test in `basics.spec.ts` moves the clock for the agent's backoff alone, 16 minutes on, as after a sleep. It aborts a list read, answers the resend with the network's expiry refusal, and checks that the read is signed anew and that no error ever shows. It also checks that the installed agent still reads the time through the getter it hooks into, so it cannot pass without testing anything after an agent upgrade.

## Upgrade notes

**Deploy only the webmail.** The backend is unchanged: this release's wasm is v0.12.2's, sha256 `462e5902a9147abb938e860f8db9c64a0df628a0684588d9311c4eb032f4798e`. So do not stop or upgrade the backend, and take no snapshot. The relay bridge is unchanged.

1. Pin v0.14.2 in the deployment repository.
2. Deploy the webmail, rebuilt with the deployment's brand. The release's unbranded `dist` hash is `dcdee2e2337754cd424bd54ad720f0626c8c702adb102bbe2a8a08b9f2855240`; the branded output differs from it.
3. Run the deployment's checks, with the wasm sha256 above.
4. Reload the webmail in each open browser. A browser may keep the old page until it is reloaded. A v0.14.0 or v0.14.1 page has Reload in its navigation; an older one has it in its header's ⋮ menu, or, on a v0.13.0 page at phone width, in its ☰ drawer.

This holds for a deployment on v0.14.1, v0.14.0, v0.13.0 or v0.12.2. A deployment on an earlier release first brings its backend to v0.12.2, and makes the changes of the releases in between, as v0.14.0's upgrade notes say. Then it deploys this webmail, with no need to deploy the webmails in between.

**Rolling back** means deploying again the webmail of the release the deployment ran before.

## Known issues

- The known issues of v0.12.0 to v0.14.0 stand, and the first of v0.14.1's: on a device whose clock is off, the agent's own first sync after a refusal does not end.
- v0.14.1's second known issue is narrowed: a network that is still down for several seconds after a phone wakes can still fail a read, with its own text, until the next refresh gets through. The agent's 3 retries wait about 1.8 to 5.3 seconds in all.
- An action whose result the agent was still waiting for when the phone woke, 5 minutes or more after it began waiting, ends with the agent's own timeout text, not the message to check whether it went through.
