# v0.14.1

## Overview

A webmail fix for a phone that wakes from sleep. A read that the network refused for its expiry showed the network's raw refusal, *Invalid request expiry: Specified ingress_expiry not within expected range…*, until the next refresh got through. The agent asks a refused request again by itself only the first time, when it sets its clock by the network's. From then on, such a read is asked again by the page, at once and signed anew, so nothing shows. The backend and the relay bridge are unchanged.

## Highlights

For people using the webmail:

- **No refusal after a phone wakes.** A request signed before the phone slept is sent when it wakes, past its expiry, and the network refuses it. The agent answers the first such refusal itself. A read refused after that is now asked again by the page at once, signed anew, up to three times more. That gets through, so nothing shows.
- **A refused action says to check it.** The page does not ask an action again, such as a star, a move or a send: one refused while its result was awaited may have run already. Past the agent's first refusal, it says *The connection to the mail server was interrupted. Check whether this went through before trying again.*
- **A refusal that lasts names the clock.** When reads signed anew keep being refused, the device's clock went off after the agent set its own by the network's. The page then says *The mail server refuses this device's time. Check that its date and time are set automatically, then reload this page.* A device whose clock is off from the start never gets that far: see Known issues.

For maintainers:

- `retrying` in `webmail/src/api.ts` asks a query again on an expiry refusal (`IngressExpiryInvalidErrorCode`). It sees only the refusals after the agent's first, which the agent answers itself by setting its clock and asking again. It finds the queries by the IDL's `query` annotations. It does not wait first, as it does for `busy:`. An update refused that way throws an error with the agent's as its `cause`.
- The page never calls the agent's `syncTime`. On a device whose clock is off, `syncTime` reads the network's time with a request that is refused in turn, and calls itself again without end. The agent's own first-time sync after a refusal is unchanged.
- Tests: two new Playwright tests in `basics.spec.ts`:
  - a list read is refused unless it comes right after a refusal, and three refreshes in a row each show their new message, with no alert;
  - a refused star says to check whether it went through, and a list read refused every time names the device's time.

## Upgrade notes

**Deploy only the webmail.** The backend is unchanged: this release's wasm is v0.12.2's, sha256 `462e5902a9147abb938e860f8db9c64a0df628a0684588d9311c4eb032f4798e`. So do not stop or upgrade the backend, and take no snapshot. The relay bridge is unchanged.

1. Pin v0.14.1 in the deployment repository.
2. Deploy the webmail, rebuilt with the deployment's brand. The release's unbranded `dist` hash is `dd7593af73e5cc864852599bedd4a7d8206a260db8d5c4700ffae76198fe414d`; the branded output differs from it.
3. Run the deployment's checks, with the wasm sha256 above.
4. Reload the webmail in each open browser. A browser may keep the old page until it is reloaded. A v0.14.0 page has Reload in its navigation; an older one has it in its header's ⋮ menu, or, on a v0.13.0 page at phone width, in its ☰ drawer.

This holds for a deployment on v0.14.0, v0.13.0 or v0.12.2. A deployment on an earlier release first brings its backend to v0.12.2, and makes the changes of the releases in between, as v0.14.0's upgrade notes say. Then it deploys this webmail, with no need to deploy v0.14.0's first.

**Rolling back** means deploying again the webmail of the release the deployment ran before.

## Webmail and settings changes

- An expiry refusal: a read is asked again, and an action or a lasting refusal is said in plain words, as above.
- `webmail/public/.ic-assets.json5`, the `brand.mjs` options, the brand format and the browser's settings are unchanged.

## Known issues

- The known issues of v0.12.0 to v0.14.0 stand.
- On a device whose clock is off, the agent's own first sync after a refusal does not end. The page keeps loading, and the agent keeps sending requests for the network's time until the page is closed. Setting the device's date and time automatically, then reloading, fixes it.
- A failed fetch or a gateway error after a phone wakes still shows its own text until the next refresh gets through.
