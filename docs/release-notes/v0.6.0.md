# v0.6.0

## Overview

A fixes release, from a review of the code shipped since v0.2.0. Expired mail in Trash and Spam is now deleted by the ingest timer in a write of its own, so Restore and Not spam never delete the mail they move, a full mailbox frees its expired mail, and one message that cannot be deleted no longer stops delivery. Spam's 30 days count from the mail's arrival. The Inbox gets an index of its own. `mail_move`, `mail_block` and `mail_unblock` reply what they did, so the webmail's notes say what the canister did, and Undo takes back only its own changes. At 1,000 blocked addresses, a new block replaces the oldest. A mailbox's quota is now at most 4 GiB. Sign-in opens Internet Identity in a popup window, so a slow sign-in with a security key no longer fails. The relay bridge is unchanged.

## Highlights

For members, in the webmail:

- **Restore and Not spam keep expired mail.** Mail in Trash or Spam past its 30 days stays listed until the cleanup reaches it. A Restore or Not spam of such mail used to delete it for good, and the move counted none of it. Now it moves like any other mail.
- **Spam's 30 days count from the mail's arrival.** Trash still keeps mail for 30 days after it left the Inbox, and a move from Spam to Trash keeps the Spam time.
  - Marking as Spam mail that arrived more than 30 days ago deletes it at once. The note says so ("Message deleted for good: it arrived more than 30 days ago"), and offers no Undo for it.
  - Undo of a Not spam deletes such mail the same way when it moves it back to Spam, and its note says so.
  - Mail already in Spam at the upgrade keeps its old time (see Known issues).
- **Notes say what the canister did.** A move's note counts the mail the canister moved, the mail it deleted for good, and the mail that was no longer there, as when another member moved it first; the list then reloads. Undo brings back exactly the mail that moved, so mail another member moved stays where they put it.
- **Undo owns only its own blocks.**
  - Spam no longer reads the list of blocked senders first, a read that could lag. Its Undo lifts only the blocks this Spam made, and Not spam's Undo blocks again only the addresses it unblocked, so a block that was there before the click stays.
  - When no mail moved but blocks changed, the note offers Unblock or Block again instead of Undo.
  - The reader's ⋮ Block sender says when the address was blocked already, and then offers no Undo.
- **Undo moves the mail back first, then the blocks.** When moving back fails before anything moved, Undo is offered again. When it fails part way, the note says what moved back, and the blocks stay as they are. When only a block or unblock fails, the note names the address and where to fix it.
- **Not spam survives the parse.** Mail a member moves to the Inbox stays there when it is parsed later, also when its `From` address is blocked. Before, such mail that was not parsed yet went back to Spam right after the Not spam.
- **Spam always blocks.** At 1,000 blocked addresses a new block replaces the oldest, where the block used to fail.
- **Block sender uses the address the canister read.** The reader's ⋮ Block sender blocks the message's `From` address as the canister parsed it, or the envelope sender when there is none. The reader's Spam and Not spam use the message as the reader loaded it, which can be newer than the list's.
- **Empty Trash and Empty Spam** walk the folder page by page, so a list that lags behind the canister neither repeats a page nor ends the walk early. The list then reloads with the search typed meanwhile.
- **Blocked senders keeps an Unblock.** The page no longer reloads after an Unblock, and hides the unblocked address for as long as it is open, so a lagging reply cannot show it again. An address blocked again shows, with its new time.
- **A search goes on past empty pages,** up to 5 calls. It then shows "No matches yet." with Keep searching, and never "No matches." while there is more to search. Keep searching goes on only from the shown search's own place, so a new search never continues where the previous one stopped.
- **Notes:** a newer note never takes over the focused button of the note it replaces, and a slow Undo's own note gives way to a newer one. A focused button in a note shows a ring in the note's text colour. An error note no longer shows the stack trace that a failed connection carries.
- **Sign-in with a security key works.** Sign-in opens Internet Identity in a popup window of 500×650 instead of a new tab. In a tab, the webmail's page was hidden, the browser slowed its timers, and the sign-in timed out after 2 seconds without a heartbeat, so a slow step, such as a security key that asks for its PIN, failed with "Channel was closed before a response was received".

For admins, in the backend:

- **A full mailbox frees its expired mail.** A delivery refused with 452 for the quota marks the mailbox, and the ingest timer deletes its expired Trash and Spam mail, so the sender's retry finds room. Before, the cleanup ran only inside a delivery or a move, and a full mailbox refused every delivery before it could run.
- **One message that cannot be deleted no longer stops delivery.** The cleanup is now a turn of the ingest timer (`ingest_clean`), up to 20 messages in a write of its own, instead of a part of each delivery and move. A cleanup that fails waits for the mailbox's next mark, while delivery and moves go on.
  - A mailbox is marked when the move of new mail into it, or a member's `mail_move`, finds expired mail there, and after a 452.
  - Cleanups take turns with moves, parses and upgrades, and with each other over the marked mailboxes, so no mailbox waits on another's backlog.
  - A move deletes nothing any more, apart from mail marked as Spam that arrived more than 30 days ago.
- **The Inbox has its own index.** Mailbox schema version 4 adds it, so listing the Inbox reads no mail in Trash or Spam. Before, the list read every newer Trash and Spam row, and failed past about 450,000 of them.
- **An unreadable list of blocked senders is not answered:** `mail_blocked` traps instead of answering an empty or partial list.
- **`control.db` has upgrade steps.** Version 2 adds the cleanup's mark, `mailboxes.clean_due`, and its index. `init` and `post_upgrade` apply the steps in one transaction, and refuse a `control.db` newer than the release.
- **A quota is at most 4 GiB.** `admin_create_mailbox` and `admin_set_quota` refuse a larger one with "quota too large", where any quota up to the largest signed 64-bit number was accepted. Mailbox schema step 4 builds the Inbox's index in one call, which fits a file of about 7.7 GB, and a 4 GiB quota of small mail makes a file of about 6 GB. The upgrade leaves existing quotas as they are: lower a larger one first (see Upgrade notes).
- An unblock that removed nothing writes nothing.

For maintainers:

- **CI:** a push to `main` reuses only the passed run of the pull request it merges, against `main` and for the same tree. A merge that changes `.github/` or the script that decides runs the tests again, and so does a run that cannot be checked.
- **Tests:** native, replica and browser tests for each change and for every review fix. The release upgrade test now starts from v0.5.0, and covers `control.db`'s step and mailbox step 4. A replica test measures the build of the Inbox's index, and fails when it would no longer fit in one call on a file of about 6 GB, the largest a mailbox of small mail reaches at the largest quota, 4 GiB.

## Candid API changes

- `mail_move : (text, vec nat64, nat64) -> (nat64)` becomes `mail_move : (text, vec nat64, nat64) -> (nat64, vec nat64, vec nat64)`: the count as before, the uids it moved, and the uids it deleted for good, which are mail marked as Spam that arrived more than 30 days ago. A uid in neither list was not there, or was in that folder already. The count leaves out the mail deleted.
- `mail_block : (text, text) -> ()` becomes `mail_block : (text, text) -> (bool)`: true when this call blocked the address, false when it was blocked already. At 1,000 addresses it replaces the oldest block, instead of trapping with "unblock one first".
- `mail_unblock : (text, text) -> ()` becomes `mail_unblock : (text, text) -> (bool)`: true when the address was blocked.
- `mail_blocked : (text) -> (vec Blocked) query` is unchanged, but traps when the list cannot be read, where it answered an empty or partial list.
- `admin_set_quota : (text, nat64) -> ()` and `admin_create_mailbox`'s `NewMailbox.quota_bytes : opt nat64` keep their types, but a quota above 4 GiB now traps with "quota too large". A null `quota_bytes` still gives 2 GiB.
- New: `ingest_clean : (nat64) -> ()`, which only the canister itself may call, as the other `ingest_` methods.

A client built for v0.5.0 keeps working: Candid lets a reply carry more results than the client reads.

## Upgrade notes

**The backend is upgraded in place, and keeps its mail.** No data is migrated, and nothing is reinstalled. Upgrade the backend first, then deploy the webmail: the v0.6.0 webmail needs the new replies of `mail_move`, `mail_block` and `mail_unblock`, while the v0.5.0 webmail works on the v0.6.0 backend. Until the new webmail is deployed, the v0.5.0 webmail reports mail marked as Spam that arrived more than 30 days ago as moved, with an Undo, although the canister deleted it. Users reload any webmail tab left open from before the deploy. The relay bridge is unchanged: nothing to copy into the bridge's app.

This holds for a backend running v0.5.0. The release upgrade test starts from v0.5.0, so a backend on an earlier release first upgrades to v0.5.0 as its upgrade notes say.

**Before upgrading, check every mailbox's `quota_bytes` and `used_bytes`** in `admin_list_entries` on the running v0.5.0 backend:

- Lower every quota above 4 GiB with `admin_set_quota`. The upgrade does not change existing quotas.
- A mailbox whose `used_bytes` is above 4 GiB needs its members to delete mail for good until it is below, before the upgrade: lowering its quota does not remove mail. Its mail could otherwise pass what schema step 4 builds in one call, about 7.7 GB of file, and the mailbox would then stay unavailable until the snapshot is restored. The build reads only the mail still stored, not the space that deleted mail left in the file, so `used_bytes` is the measure to check.

1. Stop the backend and take a snapshot (`icp canister snapshot create email-canister --environment ic`).
2. Pin v0.6.0 in the deployment repository, whose `icp.yaml` installs the release's wasm only when its sha256 matches. Upgrade the backend (`icp canister install email-canister --mode upgrade --environment ic`), and start it. `post_upgrade` takes `control.db` to version 2. The wasm sha256 is `4d35512120b7f18a0321ebfa9b8fa0fa509884a97fdae0baa9818c9b00b0b390`.
3. Deploy the webmail, rebuilt with the deployment's brand. The release's unbranded `dist` hash is `05e4fc24a2f3358ac809d79e61758f5e0e040ff3edc7cc4a3b2b709ec920e52e`; the branded output differs from it. The brand format and `brand.mjs` options are unchanged.
4. Run the deployment's checks. The ingest timer upgrades each mailbox file to version 4, one file per step, taking turns with incoming mail. The step builds the Inbox's index, so its cost grows with the file: about 5.2M instructions per MB, so one call builds it on a file up to about 7.7 GB. A mailbox of small mail filled to the largest quota, 4 GiB, is a file of about 6 GB, so every file takes one step. Until a mailbox's file is upgraded, its members' calls answer `busy:`, and the webmail says the mailbox is being upgraded. `admin_check` on each mailbox afterwards should answer `ok`. A file over about 2.6 GB does not fit in one whole-file check: check it table by table (`admin_check("<local>", opt "<table>")`).
5. Once the upgrade is confirmed, and at the latest 7 days after it, delete the snapshot (`icp canister snapshot delete email-canister <id> --environment ic`).

Expired mail from before the upgrade is deleted once the mailbox's next delivery or move finds it.

**Rolling back** is possible only by restoring the snapshot: stop the backend, restore the snapshot (`icp canister snapshot restore email-canister <id> --environment ic`), start the backend (`icp canister start email-canister --environment ic`), then deploy the v0.5.0 webmail again. A restore puts the whole canister back as it was at the snapshot, so it undoes everything since the upgrade, and only that:

- **Mail.** Mail received since the upgrade is lost. Members download their mailboxes from the webmail first.
- **Admin changes** made since the upgrade are undone: members, mailboxes disabled or purged, quotas, names, domain and bridge settings. Until they are made again, a member removed since the upgrade can read and send from the mailbox again. So before the restore, an admin prepares a script that makes those changes again, and runs it as soon as the backend is started.
- **Members' changes** made since the upgrade are undone: mail moved, filed in Spam or deleted since, by the cleanup too, comes back to where it was, and the blocks and unblocks made since are undone. Folders, blocks and read states from before the upgrade stay.
- **Sending.** Each mailbox's outbox counter goes back, so for 7 days after a message was sent on v0.6.0 a new send can get its bridge key, and the relay bridge then answers with that message's result without sending. Mail waiting to be sent in the snapshot is posted again. So restore within 7 days of the upgrade, start the canister at once, and for 7 days have members confirm important mail by another way.

Do not install v0.5.0 over the upgraded canister: it refuses `control.db` version 2 ("control.db is from a newer release"), so its `post_upgrade` traps, the install fails, and v0.6.0 keeps running. v0.5.0 would also refuse the version-4 mailbox files.

## Webmail and settings changes

- The notes of moves, Spam, Not spam and Undo, the Unblock and Block again buttons, Empty Trash and Empty Spam, Blocked senders, search and the notes' focus ring, as above. Mail marked as Spam that arrived more than 30 days ago is now reported as deleted for good.
- Sign-in opens Internet Identity in a popup window instead of a new tab. This fix is in the webmail alone, but deploy it after the backend, as above.
- The `brand.mjs` options and the brand format are unchanged.

## Known issues

- Mail already in Spam at the upgrade keeps its old time: it is deleted 30 days after it left the Inbox, not 30 days after it arrived.
- A send from a full mailbox does not free its expired mail: the send is refused, and the refusal marks nothing. Empty Trash or Empty Spam frees room at once, and the next mail that arrives, or a move of mail, starts the cleanup.
- No timer cleans expired mail by itself: a mailbox is cleaned after a delivery, a move or a 452. In a mailbox that nobody mails and nobody uses, expired mail stays listed, and can still be restored.
- Mail moved to the Inbox under v0.5.0 that is still not parsed at the upgrade goes back to Spam once when its `From` address is blocked. Not spam keeps it in the Inbox.
- At 1,000 blocked addresses, a new block replaces the oldest without saying so: mail from the oldest address reaches the Inbox again.
- The reader's ⋮ Block sender can be offered for an envelope sender that the canister refuses as an address. The block then fails, with a message that says why.
- Undo of a Spam lifts a block it made also when another member, or a second Spam click, blocked the same address right after it, as their block found the address blocked already.
- Spam blocks the `From` address the message claims, which nothing verifies. Spam that forges a real sender's address blocks that sender, whose genuine mail then goes to Spam until the address is unblocked. Only the mailbox's own domain and its subdomains are spared.
- Spam only moves the mail, and its note does not say that no block was made, when the list has no `From` address for it: mail parsed after the list was loaded (until the list's next refresh, within 20 seconds), quarantined mail, and a `From` address `mail_block` refuses.
- Not spam does not lift a block of the envelope sender, which also files mail in Spam; the next such mail goes to Spam again. Unblock the envelope sender on the Blocked senders page.
- A block or unblock whose reply is lost after the canister made it shows as failed in the note, and Undo does not take it back. The Blocked senders page shows whether the address is blocked.
- Undo of a Not spam blocks the address again in the name of the member who clicked Undo, at that time.
- Spam blocks the sender of a message that another member moved or deleted meanwhile, which the note reports as no longer here; Not spam unblocks it the same way.
- Mark unread in the list's toolbar or a row's hover action, on the message that is open, can race the reader's own mark as read, so the message can end up read. The reader's ⋮ Mark unread waits for it.
- At phone width, the device's back gesture leaves the webmail rather than returning from a message to the list. The reader's Back button returns.
- In full screen, the keyboard focus is not held inside the compose window.
- An Older mail click in Sent made while the list's first page reloads does nothing; click it again.
- A delete or move made in one browser shows in another member's list on its next refresh, within 20 seconds.
- Mail deleted for good, by Delete forever, Empty Trash or Empty Spam or after 30 days, leaves the listing and the search at once, but its bytes can stay in the mailbox file until SQLite reuses the space. A member who downloads the file can recover it with SQLite tools. A purge removes the whole file.
